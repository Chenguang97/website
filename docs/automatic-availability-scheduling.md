# 开放时间自动排程功能规格

日期：2026-11-15

状态：设计稿，供后续实现使用；本次不接入生成器，不改变现有日历、默认数据或保存行为。

本文使用以下标记：**已确定**来自本轮明确需求；**建议**是实现前可评审的设计方案；**待定**必须在对应功能开发前决策。建议与待定项不视为已经批准的产品默认值。

## 1. 功能边界与基本原则

**已确定：**教练提供工作时间、授课地点、通勤、休息和安排偏好；系统结合已有预约与锁定安排，生成开放时间草稿。教练可以修改并保存，后续新预约成立时可重新优化剩余未预约时段。

- 当前阶段继续完善同一套日历查看、手动编辑、拖选回缩、状态恢复和保存流程。自动排程后续接入这套流程，不另建一套可发布日历。
- 规则生成优先保证日程可执行，再减少不必要的通勤、折返和无法容纳完整课程的碎片。首版不预测学生需求、不承诺约满，也不承诺数学意义上的全局最优。
- 已成立的预约是固定占用，保留时间、实际授课地点和记录；生成器不能移动、取消或修改预约。
- 未预约的开放安排是可调整供给，不能当作必须回去上课的固定行程。
- 商议中的特殊请求不占用或锁定日历；形成预约后才成为固定占用。
- 生成、手动修改和重新优化都必须说明生效范围，不能把某一天的调整暗中扩散到以后每一周。

## 2. 输入与默认值

| 输入 | 已确定的规则 | 保存和复用 |
| --- | --- | --- |
| 工作时间 | 新配置默认周一至周五 06:00–17:30；支持统一设置、按天覆盖及某天不工作 | 保存为教练常用配置；不据此覆盖已有实际安排 |
| 生成日期 | 默认当前查看的一周；明确日期范围、生效日期以及指定日期 / 每周重复 | 每次生成和应用都展示范围；重复规则需有明确生效边界 |
| 可授课地点 | 自动读取个人资料选定的冰场；本次可进一步缩小范围 | 常用限制可保存；资料变化后检查失效地点 |
| 地点可用窗口 | 支持为某冰场指定可授课日期、星期和时间范围 | 区分教练确认、外部数据和未知；未知不能当作全天可用 |
| 冰场间通勤 | 提供可修改、可保存的估算；区分方向与出发时段 | 保存来源、更新时间和教练覆盖值；缺失值不按 0 计算 |
| 同冰场课间间隔 | 与跨场通勤分开设置，允许 0 分钟连续上课 | 默认值待定，不从跨场通勤字段推导 |
| 午餐 | 可不预留；也可固定时段，或在指定窗口内安排所需时长 | 例如 12:00–14:00 内连续 30 分钟；是否预留由教练选择 |
| 其他必须休息 | 支持单独的固定占用或带时长的可安排窗口 | 与系统通勤分别存储，保留手动来源与锁定状态 |
| 地点偏好 | 优先冰场、希望顺序；必须区分“尽量满足”和“必须遵守” | 保存常用偏好；每次可临时调整 |
| 已有事实 | 自动读取已有预约、课程时长、锁定安排和当前开放草稿 | 不要求重复填写；生成时记录所用数据版本 |

### 2.1 输入有效性

- 工作时间、地点可用窗口和休息窗口使用明确日期 / 星期与时区；结束时间必须晚于开始时间。跨日窗口的具体支持范围应另行定义，不能默默截断到当天。
- 生成的新开放时段必须同时落在工作窗口、地点可授课窗口以及允许生成的未来日期范围内。
- 冰场营业时间不等于允许外教授课的时间。需要区分“冰场营业”与“教练可在此授课”的已知条件。
- 缺少某冰场可用窗口时，提示教练补充或将该冰场排除出本次排程；可以继续生成不依赖该未知条件的部分。
- 资料中可去其他冰场协商，不等于本次已获准在所有冰场自动开放。特殊请求提出的新地点也必须有本次可行性依据。
- 同一冰场不计算跨场通勤；同场课间间隔的 0 是合法设置。不同冰场缺失估算时，状态是“需补充”，而不是 0。
- 不计算住宅到首个冰场及末个冰场回家的通勤；但工作窗口之外已有的相邻预约，仍可能约束窗口内的新开放时段，不能因为它在工作时间外就忽略。

### 2.2 通勤输入的含义

**已确定：**A → B 与 B → A 可以不同；不同出发时段可以使用不同估算。教练可主动修改估算后重新检查。

**建议：**将截图中的自由文本“方向通勤表”转为结构化规则：出发地点、到达地点、适用星期 / 日期、出发时间段、分钟数、来源、更新时间。使用教练明确保存的覆盖值，其次使用适用的默认数据；仍无法确定时要求补充。不能把不适用的方向或时段当作可靠回退值。

**待定：**默认通勤数据来源，以及估算是否包含停车、换装备等额外转换时间。界面必须与数据口径一致，不能把一个写死的示例分钟数标为实时路线结果。

### 2.3 “不限冰场”与线上课程

现有“其开放冰场不限”与“预约实际地点”需要分开理解。

**建议：**自动排程内部使用明确物理地点计算行程；“不限冰场”不能作为免通勤的实际地点。若保留对外的灵活地点开放，预约确认时也必须解析实际冰场并完成可行性校验。

**待定：**Zoom 等线上课程参与自动排程时，教练实际所在地点如何确定。线上课不能让教练在两个冰场之间瞬移；在该语义明确前，不利用线上课消除跨场通勤。

## 3. 固定约束与优化偏好

| 层级 | 约束 / 目标 | 处理方式 |
| --- | --- | --- |
| 固定事实 | 已成立预约的起止时间、实际地点 | 原样保留，任何生成结果都不能改动 |
| 必须遵守 | 教练锁定的时段 / 地点、必须休息、硬性地点顺序、地点可用窗口 | 新安排必须满足；不可行时返回原因，不静默放松或丢弃 |
| 新安排可执行性 | 不重叠、完整课程、同场间隔、跨场通勤、工作时间 | 约束新开放与新预约；未知必要数据不能当作满足 |
| 尽量满足 | 优先冰场、期望顺序、希望少换场 | 在满足固定约束的候选方案中比较 |
| 默认优化目标 | 少通勤、少折返、少无效碎片 | 对可调整部分优化，不通过改动已有预约换取评分提升 |

**建议的比较顺序：**先满足固定约束，再减少通勤与折返、减少无有效课程起点的碎片，并考虑教练偏好和对现有安排的改动量。软目标之间的具体权重待定；结果要能解释取舍，不能为了凑开放分钟数制造无意义往返。

“锁定”必须说明锁定什么：时间、地点，或两者。未预约开放时段上的地点锁定，同样是必须保留的安排；解除锁定必须由教练明确操作。

若两个硬约束互相矛盾，不通过优先级覆盖其中一个。例如锁定休息与已有预约冲突，系统保留预约和规则事实，说明该段无法新增安排，交由教练调整可修改的规则。

## 4. 已有预约不追溯套用新规则

**已确定：**后来修改的通勤或休息规则主要约束新开放安排与新预约。

- 不因新规则而移动、取消已有预约，也不反复把旧预约组合标成新的冲突待办。
- 旧预约继续作为固定占用，且其实际地点必须参与前后新时段的通勤计算。
- 若相邻旧预约在新规则下已经没有可接课的间隙，该间隙不生成新的开放时段；其他日期和可行部分仍可排程。
- 不能因一对历史形成的固定安排不满足新通勤规则，就判整周无法生成；也不能借“不追溯”豁免后来插入的新课程。
- 需要解释未生成原因时，轻量说明“此空档不足以新增完整课程及所需通勤”，不持续要求教练修改旧预约。
- 必须休息的窗口已被旧预约占满时，说明该窗口无法安排新的休息 / 开放方案，允许修改休息条件或保留该日现状；不能擅自删掉必需休息，更不能挪动预约。

**建议：**记录新预约确认时使用的规则版本与校验结果；兼容导入的旧预约按固定事实处理。规则版本变化不批量重发旧冲突提醒，但任何后来新增的课程都按当前适用规则检查。

## 5. 新预约的统一可行性检查

普通预约、允许的自助修改、特殊请求接受，后续都应调用同一套纯规则校验。正常公开条件内可行的自助修改，仍走原流程，不强制变成商议。

检查依据必须是最新已成立预约、锁定安排、实际地点、适用规则及对外开放状态，而不是旧预览截图。

### 5.1 检查内容

1. 课程起止有效，时长对应可用课程；不与其他课程或必须保留的固定占用重叠。
2. 授课地点确实允许，且在相应可用窗口内。只在 A 开放的时段不能直接按 B 的普通预约成立。
3. 与最近前后固定安排均能衔接；必要时包含到达下一地点前必须完成的中间占用。
4. 同冰场满足独立设置的课间间隔；跨冰场使用适用方向和出发时段的通勤值。
5. 存在可执行的实际移动路径，且通勤与不可重叠的吃饭 / 休息没有被重复计作同一段时间。
6. 新预约及必要的开放收紧可以一起可靠提交，不能先报接受成功再留下失效的可预约时段。

对相邻课程的简化检查为：

```text
同场：前一课程结束 + 同场课间间隔 ≤ 新课程开始
跨场：存在出发时间 d ≥ 前一占用结束，使 d + 通勤(出发地, 到达地, d) ≤ 新课程开始
```

后向到下一固定安排也做同样检查。实际还需扣除必须休息等独立占用；不能只分别核对两个间隔的分钟数就认为整段可行。

未指定地点的休息不能重置教练的实际位置或免除通勤；安排休息时需保持前后路径连续。

**建议的失败反馈：**说明相关预约 / 固定安排、方向、适用通勤估算、可用间隔和缺口，例如“09:40 在 A 下课，10:00 在 B 上课；需要 30 分钟，现有 20 分钟，缺少 10 分钟”。缺失通勤数据时明确显示“尚未配置 A → B 的通勤估算”。

教练调整通勤估算后可重新检查；无论估算如何修改，课程时间本身都不能重叠。

### 5.2 提交一致性

**建议的实现要求：**确认前用最新数据再校验；预约写入、必要开放收紧及其关联通勤更新使用一个一致的提交过程。数据版本变化、预约被抢占或存储失败时，保留当前输入并重新检查，不能显示虚假的成功。

当前原型的前端存储不等于生产环境的并发预约保障；后续正式服务端提交也必须执行同一业务约束，不能只依赖浏览器检查。

## 6. 特殊请求插入与后续地点选择

### 6.1 接受流程

```text
商议中（不占时段）
  → 接受前检查最新固定安排、地点可用性与通勤
  → 不可行：说明原因，调整方案或通勤估算后重查
  → 可行：展示本次预约及必要开放调整的影响
  → 确认成功形成预约
  → 重新计算相关通勤，并对剩余未预约时段生成优化结果
```

修改已有预约的特殊请求在新方案真正达成前，原预约持续保留；请求到期或结束也不自动取消原预约。最终校验修改方案时，不能把被替换的原预约误当作另一节外部冲突课程；替换成功前又不能释放它供别人预约。

### 6.2 A / B 示例

前提：09:00–12:00 原计划在 A 开放；拟接受 10:00–10:30 在 B 的预约。示例中两个方向的通勤都明确为 30 分钟，不据此假设所有方向天然对称。

| 部分 | 结果 |
| --- | --- |
| 到 B 前在 A 授课 | 前一课程最晚 09:30 结束；09:30–10:00 用于 A → B |
| B 的课程 | 固定为 10:00–10:30 |
| 后面必须回 A | 10:30–11:00 预留 B → A；最早 11:00 在 A 授课 |
| 后面只有未预约 A 开放 | 不把返回 A 当作硬要求；比较继续在 B、返回 A、去下一地点 |

是否值得返回 A，还要检查返回后可授课窗口和完整课程时长；不能因为旧开放块写着 A，就机械恢复 A。

### 6.3 不机械折返的分支

| B 插入位置及后续安排 | 应用规则 |
| --- | --- |
| 位于 A 开放段尾部 | 优先考虑在 B 结束该段；不为少量未预约的 A 剩余时间折返 |
| 后面已有 A 的预约 / 锁定必须在 A | 返回 A 是固定约束，先留足通勤再判断能否接 B |
| 后面只是未预约的 A 开放时间 | A 部分可重分配；比较留在 B、回 A 或前往下一冰场 |
| 回 A 后不足以容纳完整课程 | 通常不回；B 确认可授课时可继续在 B 开放，否则可不新增开放 |
| 后面有 C 的固定安排 | 直接评估 B → C，不能默认绕回 A |
| B 后续可用窗口未知 | 不凭空延长 B 开放；补充条件或输出其他已知可行部分 |

“优先留在 B”是优化取向，不等于必须留在 B；锁定约束、地点可用性和实际通勤可能得出其他结果。

## 7. 日历、草稿、手动修改与发布

### 7.1 接入当前开放时间页面

**建议：**保留已确认的日历 / 表单切换、地点设置、拖选和公共保存入口。后续增加轻量“自动排程”入口，配置工作时间、通勤、休息和偏好；生成结果回到同一日历草稿中，不覆盖式替换整个工作区。

日历对开放授课、已有预约、通勤、休息分别使用文字 / 图标与适当样式，沿用地点颜色。不能仅靠深浅颜色区分四种状态，也不恢复此前已删除的常驻大图例。

- 已有预约仍显示时间、实际授课地点与必要状态，保持不可被开放时间拖选修改的属性。
- 通勤块显示 A → B、时间、估算来源，能关联查看依赖的预约 / 安排。
- 休息块标明手动 / 规则生成及锁定状态，与通勤保持不同类型。
- 生成结果明确标为未保存草稿；提供生成范围和变更摘要，解释哪些时段新增、缩短、移场、删除或未生成。

### 7.2 手动修改保护

**已确定：**教练可以调整地点、起止时间、午餐长度、通勤估算，并可锁定；系统不能在编辑后立即改回。

**建议：**手动修改标记来源，在本轮草稿中保留；如果再次主动生成会影响未锁定的手动修改，先列出变化并允许保留 / 锁定，不能无提示覆盖。后台新预约触发优化时，产生待比较建议，不直接改写教练正在编辑的草稿。

- 锁定部分重新生成时保持原样；只能由教练明确解锁。
- 调整通勤块时实际修改其估算 / 适用规则并重查衔接；不能只是缩短图形，却继续使用旧通勤值判断。
- 缩短午餐也应更新休息时长 / 规则；若低于教练设置的必需时长，要求明确修改规则。
- 拖选回缩恢复手势开始前的状态，包括之前未保存修改；Esc / 指针取消只取消本次手势。
- 保留撤销、保存中防重复提交、失败保留草稿、成功后再显示已保存及离开保护。
- 生成本身不更新对外开放。教练确认保存后才发布相应范围，且不能顺带更改未选择的日期或重复模板。

### 7.3 新预约后的收紧与优化分开

**必须满足的边界：**新预约已成立后，不再可执行的旧开放时段不能继续接受预约；同时不能默认静默把剩余开放改到其他冰场。

**建议、待确认的交互方案：**

1. 接受前展示必须收紧的原开放与必要通勤占用，由本次接受确认一并提交。这属于保证新预约可执行的影响，不是自由优化后的地点发布。
2. 继续在 B 开放、返回 A 或改去 C 等可选择的重新分配，先作为建议草稿供教练确认。
3. “优化建议自动发布”是否可选、默认什么模式，另行确定；未确认前不实现自动发布优化结果。

即便将来允许自动发布，也必须有明确的教练授权、变化记录及手动 / 锁定保护。缩减不可行供给与新增 / 变更地点的权限不能含糊地共用一个自动开关。

## 8. 每周重复规则与指定日期

**已确定：**生成范围默认所查看的一周；应用时明确生效日期及“仅指定日期 / 每周重复”。不能把当前一周与无限期每周生效混为一谈。

**建议：**将规则分成三层，具体覆盖语义待确认后实现：

| 层 | 责任 |
| --- | --- |
| 每周基础模板 | 教练明确保存的常规工作与开放安排，带生效日期边界 |
| 日期覆盖 | 某一天的开放调整、临时休息及一次性预约带来的衔接调整 |
| 固定占用 | 已成立预约和明确锁定的安排，参与生成与可行性检查，不能被模板覆盖删除 |

先由模板与日期覆盖形成当天计划，再结合固定占用及规则求可行剩余时间。两个硬约束冲突时返回原因，不通过“后覆盖前”删除其中一个。

**建议：**一次性预约引起的调整仅写入对应日期，不回写每周模板；主动修改模板才影响后续所选重复日期。模板变化时遇到已有日期覆盖，应展示受影响范围并保留或要求教练选择，不暗中清空。

## 9. 通勤与休息的来源、关联和生命周期

**建议的数据职责：**至少能区分记录类型、起止、地点 / 路径、适用日期、来源、锁定内容，以及关联的预约 / 计划段标识。具体字段名在实现时按现有模型收敛，不为此建立第二份预约事实。

| 类型 / 来源 | 重新计算时的处理 |
| --- | --- |
| 系统生成通勤 | 关联前后预约或计划段及所用通勤规则；依赖取消、改期、换地点后重新计算或移除 |
| 教练手动休息 | 独立占用；不能因为与某通勤时间重合，就被当作失效通勤删除 |
| 规则生成午餐 | 关联午餐规则和当前日期；遵守手动修改与锁定保护 |
| 教练锁定的行程 | 作为必须保留的安排，不能随系统通勤清理；失去原依赖时说明原因供教练处理 |
| 未预约开放 | 按日期与模板范围调整；来源和锁定状态可追踪 |

重新计算按记录类型、来源与依赖标识处理，不能按灰色外观、相同时间范围或文本包含“通勤”来判断可删除对象。预约取消后也不机械恢复旧 A 开放，仍按当前规则检查可行性。

## 10. 课程时长与碎片有效性

**已确定：**读取已有课程时长；不能生成容纳不了完整课程的可预约选项。某段时间够一节课，还不代表前后通勤与休息也可行。

**建议、待确认：**按教练本次启用的课程时长集合计算合法课程起点，而不一律使用 30 分钟或最长课程时长：

- 连续同地点可授课窗口内，完整容纳课程，并满足前后通勤 / 同场间隔，才是该课程的合法起点。
- 至少一种可预约课程存在合法起点，才将该段作为有效开放供给；同时保留各课程的可约范围。
- 20 分钟空档对 30 分钟课程无效，但如果启用了 15 分钟课程且衔接可行，可能有效。
- 45 分钟连续窗口不能只因课程是 60 分钟而全部删除；也不能把仅够 30 分钟的窗口展示为可约 60 分钟。
- 锁定的手动时段不足以授课时保留锁定事实，但不对外伪装成可预约课程。
- 内部计算按分钟处理，日历显示与可约起点的网格另行确定；不能将 28 分钟通勤向下取整而生成不可执行的预约。

**待定：**使用哪些课程时长、可约起点对齐粒度、是否允许教练设置最小有意义开放长度，以及多个有效方案之间如何评价碎片。

## 11. 规则生成与增量优化流程

**建议的首版流程：**

1. 读取最新已保存配置、当前编辑草稿、预约和锁定安排，并明确这次使用哪个配置版本；个人资料有未保存修改时提示，不混用两份地点配置。
2. 确定生成日期 / 重复范围，检查缺失地点窗口、通勤数据和相互矛盾的必需规则；返回可修复项。
3. 将已有预约、锁定安排及固定休息放入每天时间线。旧预约的既有不可行衔接只限制新供给，不触发追溯更改。
4. 在可行空档内安排必需的弹性休息，比较地点路径，预留通勤与同场间隔，再计算完整课程起点。
5. 对不违反硬约束的候选方案，按减少通勤、折返、碎片及偏好等指标比较；相同输入应得出稳定结果。
6. 返回草稿、必要通勤 / 休息、与旧计划的差异、未生成原因和所用数据版本。无解部分可以保留现状或待调整，不能静默牺牲硬约束。
7. 保存 / 发布前再校验最新预约版本；有变化时合并或提示重算，不用旧草稿覆盖新预约。

新预约、改期或取消后，先计算对应日期内受影响的前后固定安排之间的区间；若影响跨越该区间，再明确扩展计算范围。保留其他预约和锁定部分，不默认整周重新洗牌。

对已发布开放段的边界也要检查：不能允许 A 的最后一节课与 B 的第一节课紧邻却没有通勤。每次确认预约仍必须再次校验，不能只依赖生成时的一次检查。

## 12. 实现阶段与现有代码衔接

| 阶段 | 范围 | 完成条件 |
| --- | --- | --- |
| 当前阶段 | 日历查看、手动编辑、拖选回缩、草稿恢复、保存及预约参考 | 以现有开放时间流程稳定性为先；不宣称自动通勤规则已启用 |
| 规则与输入阶段 | 明确待定决策；建立结构化配置、日期 / 重复范围、来源和锁定语义 | 配置可以保存复用；统一纯可行性校验具备行为测试 |
| 手动触发生成阶段 | 一键生成当前范围草稿、原因说明、手动调整、锁定、确认保存 | 不移动旧预约；不静默发布；未知必要条件不伪装可行 |
| 预约事件优化阶段 | 确认前校验；新增 / 改期 / 取消后的关联通勤与剩余开放更新 | 先解决提交一致性，再按已确认模式提供建议或自动发布 |

### 12.1 当前实现事实

- 当前开放时间与预约管理共用周历网格和预约覆盖层，但编辑、渲染与保存归属各自功能目录。
- 当前默认开放配置中仍有 06:00–16:00；本设计的 06:00–17:30 是后续新增排程配置的默认值，本轮不改现有保存数据。
- 截图中的预约确认、提前时间、通勤数字与方向文本，当前未接入排程约束及相应配置保存，不能当作已经生效的自动规则或可靠路线数据。
- 当前数据按 30 分钟网格编辑；后续生成器需明确分钟级通勤和不同课程时长与此网格的关系，不能直接沿用网格步长作为所有业务时长。

### 12.2 架构约束

实现时继续遵守 `AGENTS.md` 与 `docs/architecture.md`：纯排程与可行性规则放在 `js/domain/`，不依赖 DOM、浏览器存储或可变应用状态；绑定运行时事实只通过 `js/core/scheduling-rules.js`。开放时间交互放在 `js/coach/availability/`，预约与特殊请求提交仍由对应预约功能负责。

业务事实保持单一所有者；持久状态在 `js/core/state.js`，存储访问在 `storage-adapter.js`，序列化 / 兼容恢复在 `data-store.js`。渲染不保存数据，不新增生产全局变量，不复制学生端或第二份预约工作区。

## 13. 正式实现前的决策清单

| 决策 | 当前结论 | 建议 / 需要明确的问题 |
| --- | --- | --- |
| 通勤默认数据来源 | 待定 | 覆盖地区、方向 / 时段、有效期、失败回退、是否包含停车换装；需评估来源后确认，不填写虚构默认数据 |
| 同冰场课间间隔默认值 | 待定；允许 0 | 可讨论默认 0 分钟连续授课，教练可改；尚未批准 |
| 新预约后的发布模式 | 待定 | 建议自由优化先待确认；接受预约所需的开放收紧单独明示并提交 |
| 模板与日期覆盖关系 | 待定 | 建议一次预约只影响对应日期；明确重复生效边界、日期覆盖与模板编辑冲突的处理 |
| 完整课程 / 碎片判断 | 待定 | 建议按启用课程集合的合法起点判断；确定课程集合、起点网格及碎片目标 |
| 软目标权重 | 待定 | 通勤分钟数、换场次数、碎片和偏好发生取舍时的比较顺序 |
| 地点可用窗口依据 | 待定 | 教练确认与外部数据各自的责任、更新时间、未知时的操作方式 |
| 线上 / 不限冰场参与方式 | 待定 | 明确实际物理地点与对外灵活地点的预约校验语义 |

前五项是本轮明确提出的实施前决策；其余是为避免实现时暗中补规则而补充的边界问题。本轮不要求教练立即回答，不阻塞当前手动日历维护。
